Retbleed · Return Target Prediction

A RET can transiently go to a wrong target even though the saved architectural return address was never changed.

First understand the mechanism

Affected transient behavior
Briefly execute R_OTHER

CALL worker records a return address R_OK. At RET the machine may start fetching a predicted target before the real return resolves. Retbleed shows affected return-prediction paths on particular Intel and AMD implementations. In the model, R_OTHER is a symbolic wrong target; it does not replace the saved address. Once the return resolves the wrong path is discarded, but an executed disclosure gadget may have left a trace.

Follow the teaching example

Numbered semantic pseudocode, not a runnable attack. Labels and values are illustrative; it does not configure predictors, manufacture faults or decode secrets. The diagram is conceptual, not a measured timing trace.
[01] CALL worker; saved return = R_OK
[02] worker executes; saved return remains R_OK
[03] RET
[04] affected prediction: target = R_OTHER
[05] transient: instructions at R_OTHER may execute
[06] architectural: return to R_OK

The saved address in [01] remains unchanged in [02] and [06]. What differs is the early prediction at [04]. This is why the model should not be read as a stack-smashing or software-return-address attack.

What is trained or triggered?

The relevant state is return/target prediction. On evaluated Intel designs RSB underflow is important; the documented AMD behavior is not captured by that same rule. Do not turn one implementation’s trigger into a universal statement about every RET.

Prerequisites and trust boundary

The attack needs a reachable return and suitable victim code under the evaluated predictor-sharing conditions. Kernel-disclosure demonstrations do not establish identical behavior on newer or differently configured CPUs.

What does the mitigation interrupt?

Use the model-specific microcode and kernel return-path defenses, including applicable return thunks, RSB handling or hardware controls. Retpoline’s use of returns does not prove protection where returns themselves take an affected target-prediction path.

Do not confuse these concepts

A prediction problem is not a stack overwrite or ROP modification of the architectural return address. BHI focuses on history selection; Retbleed focuses on the return instruction’s prediction path.

How to read the original material

Read the research team’s Intel and AMD conditions separately. Follow the return instruction, prediction source and eventual saved address through the argument; then examine the matching kernel defense.
