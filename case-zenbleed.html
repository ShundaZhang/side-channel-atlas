Zenbleed · Register Lifetime / Recovery

On affected Zen 2 cores, a vector-register recovery bug can expose stale data architecturally, without a cache-timing receiver.

First understand the mechanism

Trigger
Affected speculative register recovery
Data / prediction source
Reused physical vector-register data
Architectural result
Restore this context’s valid register state
Affected transient behavior
Wrong lifetime/recovery state may escape

Architectural registers are names backed by renamed, reusable physical storage. An architecturally executed VZEROUPPER clears upper vector state, but if it was on a mispredicted path, recovery must restore the valid state from before that operation. The original report connects incorrect lifetime/recovery bookkeeping to exposure of stale physical-register data. Our example calls the correct current-context state SELF and unrelated stale content OLD. Unlike the other sampling models, the bug can make OLD architecturally visible.

Follow the teaching example

Numbered semantic pseudocode, not a runnable attack. Labels and values are illustrative; it does not configure predictors, manufacture faults or decode secrets. The diagram is conceptual, not a measured timing trace.
[01] this context’s valid upper state = SELF
[02] wrong-path VZEROUPPER must not commit
[03] affected register lifetime/recovery event
[04] correct recovery must restore SELF
[05] bug outcome: later architectural read may expose unrelated OLD
[06] this readout does not require cache timing

The bug outcome in [05] is an architectural read, unlike the discarded transient samples in MDS and RFDS. Compare it with the correctly restored SELF in [04], not a hypothetical committed zero. This exception is why the guide does not equate every disclosure with cache timing.

What is trained or triggered?

The original bug involves specific execution/recovery conditions, not a generic V1/V2 branch-training story. The explanatory model does not supply an instruction recipe for those conditions. The data readout itself need not reconstruct a cache channel.

Prerequisites and trust boundary

Affected Zen 2 implementations can expose data from other work using the shared physical register resources under the reported conditions. Confirm the exact AMD product and update state; do not generalize to all AMD generations or assume SMT is always the only boundary.

What does the mitigation interrupt?

Install applicable AMD/OEM microcode or firmware updates. Treat any documented workaround as model-specific rather than as a substitute for verifying the supported fix. A cache flush does not explain or repair this register-lifetime bug.

Do not confuse these concepts

This is the taxonomy exception: a speculative precursor can lead to an architecturally visible stale-register value. The other sampling models discard their transient sample as an architectural result.

How to read the original material

In the original report, distinguish architectural register names, physical storage and recovery bookkeeping. Its significance is precisely that not every microarchitectural disclosure ends in a cache-timing channel.
