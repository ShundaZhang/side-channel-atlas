Spectre V2 · Branch Target Injection

The real function pointer stays intact; the CPU may temporarily fetch instructions from a different predicted target.

First understand the mechanism

Trigger
Indirect target not ready
Data / prediction source
Victim code at predicted gadget
Architectural result
Branch to NORMAL
Affected transient behavior
Execute GADGET first

Keep three code addresses separate: the indirect branch at 0x401240, the real target 0x402180, and a desired predicted gadget at 0x4030A0. These are teaching addresses in the victim’s virtual address space. Before the true target resolves, target prediction can redirect transient execution to the gadget. Resolution restores the correct destination; it does not undo every microarchitectural effect of the wrong path.

Paper instruction + teaching context (32-bit x86)

01  mov eax, [normal_target_slot]  // Teaching load; EAX gets NORMAL
02  jmp eax  // Paper instruction: indirect branch
03  // predicted target: GADGET  // May fetch wrong code before resolution
04  // GADGET uses victim-accessible data  // A wrong target alone is not a leak
05  // real target resolves: NORMAL  // Discard wrong-path register results
06  // architectural target slot unchanged  // No function-pointer overwrite

Numbered semantic pseudocode, not a runnable attack. Labels and values are illustrative; it does not configure predictors, manufacture faults or decode secrets. The diagram is conceptual, not a measured timing trace.
[01] branch PC = 0x401240
[02] real_target = NORMAL        # 0x402180
[03] predict_target() = GADGET   # 0x4030A0, teaching label
[04] transient: GADGET uses victim data
[05] resolve real_target
[06] architectural: execute NORMAL; discard wrong path

In [01] the number identifies the branch instruction itself. In [02] it identifies the correct destination; [03] names different code. None is the secret-data address. The crucial contrast is [04] versus [06], not a corrupted pointer.

What is trained or triggered?

The attacker influences target-prediction state and applicable history/context. The mapping of branch PCs, histories and targets is implementation-specific. Do not assume the attacker’s training-side address must equal the victim gadget’s full virtual address.

Prerequisites and trust boundary

A usable gadget must read victim-accessible data and encode an observable effect. Cross-process, user/kernel and guest/host attacks have different predictor-sharing and execution prerequisites. Merely causing a target misprediction is not yet secret recovery.

What does the mitigation interrupt?

Use the CPU- and boundary-specific combination of indirect-branch hardening and predictor controls, such as applicable retpoline, IBRS/eIBRS, IBPB and STIBP. These mechanisms act at different places; later BHI and return-prediction findings limit blanket claims about any one defense.

Do not confuse these concepts

The gadget address is code, not the secret-data address. BTI changes prediction, not the architecturally stored function pointer.
