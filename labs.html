01 / SIMULATOR

Why can’t one timing sample establish a cache hit?

This is an instructional model with adjustable noise, the numbers do not represent the number of cycles of any real CPU. Observe how distributions overlap and decisions go wrong.

Hit / Miss timing model

Generates a fixed 100 samples for each class. Change the "noise" and threshold and observe the decision accuracy.

What you should observe

When the noise increases, the two sets of samples overlap and the judgment accuracy decreases. Shifting the threshold to one side will increase a certain type of misjudgment.

Real experiments require controlling thread positions, warm-up, timers, prefetch effects and counting repeated experiments. "Vulnerable/Mitigated" in machine reports cannot be inferred from this animation.

This model has no real flush, branch prediction or secret read, and is only used to explain why the paper reports multiple sampling, error rate and signal-to-noise ratio.

02 / SIMULATOR

Why can rollback still leak?

Step through a simplified Spectre V1 story. All values ​​are teaching constants within the page.

0 / Attacker training: check usually passes
1 / CPU tentative prediction: also passes this time
2 / Wrong path: read toy secret = 3, touch probe[3]
3 / Check failure: Undo the wrong path architecture result
4 / Measurement: probe[3] is still hot in the model

What does the model leave out?

Real core ROB, load dependencies, branch predictors, cache levels, fault handling, and noise that require a large number of repeated measurements. The page never attempts to trigger native Spectre.

03 / LOCAL BASELINE

Measure a cache line on your own machine

The repository provides a minimal x86-64 teaching program, which only compares cached and flushed access times for the process's own buffer, without crossing permission boundaries.

How to run (x86-64 Linux / macOS)

git clone https://github.com/ShundaZhang/side-channel-atlas.git cd side-channel-atlas cc -O2 -Wall -Wextra examples/cache_timing.c -o cache_timing ./cache_timing ./cache_timing --csv > timings.csv

Use native x86-64 hardware with CLFLUSH and RDTSCP. The default output reports medians in TSC ticks; CSV preserves the acquisition order of the cached/flushed pairs. The fixed paired order is useful for a baseline, and a stronger comparison should randomize conditions across independent runs. cache_timing.c ↗

Experiment log template

Note down the CPU model, operating system, compiler, virtualization or not, hit/miss median, number of samples, and "observed/unobserved" differences.

Don't claim that "side channels do not exist on this platform" just because the difference is not significant. This program does not detect vulnerability, nor does it evaluate system mitigations.
