Inception / SRSO

Speculation can train later return predictions, so recovering from one wrong path does not remove the predictor state it created.

First understand the mechanism

Trigger
Phantom speculation and return prediction
Data / prediction source
Predictor state trained transiently
Architectural result
Real return address remains R_OK
Affected transient behavior
Later RET may go to a wrong gadget

The Inception study combines phantom speculation with training in transient execution. A location need not architecturally be a CALL to contribute CALL-like speculative effects on an affected implementation. The resulting return-prediction state can influence a later RET. The teaching sequence below treats these effects as events; it is not an instruction sequence that constructs a real overflowing predictor. The eventual return target remains architecturally correct.

Follow the teaching example

Numbered semantic pseudocode, not a runnable attack. Labels and values are illustrative; it does not configure predictors, manufacture faults or decode secrets. The diagram is conceptual, not a measured timing trace.
[01] architectural code has a real return R_OK
[02] event: affected phantom speculation opens a window
[03] transient activity influences return-prediction state
[04] later RET predicts a wrong GADGET
[05] transient: GADGET may run
[06] architectural: return to R_OK; prediction effects are separate

Keep [02], [03] and [04] as separate stages. The first transient window can influence predictor state used later. Neither [03] nor [04] means that the saved software return address changed.

What is trained or triggered?

The distinctive point is that transient activity can train future predictions. This differs from merely executing legal indices before a V1 check. The exact BTB/return-predictor interaction depends on AMD microarchitecture.

Prerequisites and trust boundary

The original research evaluates AMD Zen scenarios, including user/kernel disclosure. Separate the paper’s threat model from the exact vendor support matrix and kernel state. A stale prediction by itself is not a recovered secret; a usable gadget and observation channel are still needed.

What does the mitigation interrupt?

Use the relevant microcode and kernel SRSO return-path protection. Linux distinguishes extended IBPB from Safe RET and boundary-specific combinations. One control’s presence does not establish protection of user/kernel, guest/host and user/user transitions equally.

Do not confuse these concepts

Retbleed also concerns RET prediction, but Inception highlights phantom speculation and transient training of later predictions. Neither requires rewriting the software return address.
